# Аудит VIP Champ и устранение замечаний

Дата: **20 октября 2026**, часовой пояс Asia/Seoul. Исходная проверенная ревизия:
`1f360a4`. Документ описывает исправления кода и подготовленную инфраструктуру;
**запуск реального бота ещё не выполнен**. По последнему уточнению пользователя
нужен новый запуск с пустой БД: старый бот не работает, исходных настроек и БД
для переноса нет. Миграция legacy-данных для этого развёртывания не требуется.

Проверены рабочие Python-модули, сценарии администрирования и импорта,
зависимости, Docker/Compose и отслеживаемые Git файлы. В исходном репозитории
было 346 tracked-файлов, включая 330 снимков `.history`. Аудит и тесты не доказывают
отсутствие любых возможных ошибок; ниже перечислены подтверждённые проблемы и
конкретные меры.

|---|---|---|

При повторном независимом ревью дополнительно устранены: сохранение сессии
после смены пароля/роли/привязки, возможность занять непривязанный legacy-аккаунт,
сохранение некорректного plaintext `password_hash` в quarantine, гонка отзыва
полномочий во время административной записи, конкурирующее восстановление
рассылок двумя процессами и пропуск освобождения ресурсов при ошибке удаления
heartbeat. Для legacy-администраторов теперь требуется явная привязка через
доверенный CLI; владелец данного развёртывания — Telegram ID `556399210`.
Один только ID не даёт доступа.

## Проверки и пределы подтверждения

- На Linux подтверждены **95 отдельных тестов и 15 subtests**, включая все
  6 сценариев deployment/rollback и 11 lifecycle-тестов. Число учитывает
  основной прогон и повторный прогон исправленных lifecycle-тестов; полный
  CI на конечной ревизии ещё предстоит. Также пройдены ruff, разбор трёх
  YAML-файлов, `bash -n` трёх shell-скриптов и `git diff --check`.
- Оба lock-файла прошли `pip-audit`: известных уязвимостей не обнаружено на
  момент проверки. Это проверка Python-зависимостей, а не всего Docker-образа.
- Текущая рабочая версия tracked-файлов прошла сканер секретов. Полная проверка
  очищенной истории должна быть выполнена после её переписывания.
- Тесты deployment/rollback используют подставной Docker и не доказывают
  успешную доставку образа в рабочую среду. Отдельно выполнен реальный `pg_dump`
  с нового LXC: резервная копия инициализированной рабочей БД — 20 152 байта.
  Полное восстановление именно этой копии ещё требуется подтвердить.
- Создание LXC, БД или успешные локальные тесты не означают завершённый выпуск:
  нужен результат CI для конечного commit, совпадение runtime revision
  и успешная работа бота с Telegram.

## Что ещё требуется для завершения

1. Получить действующий **заменённый** Telegram-токен через внешний секретный
   конфиг; найденные исторические значения повторно не использовать.
2. Завершить очистку Git-истории и её проверку; выполнить CI на конечной ревизии.
   История исходного кода сохраняется за исключением запрещённых путей;
   отдельная копия исходных секретов не создаётся. Для контроля сохраняются
   только метаданные Git refs до очистки.
3. Подтвердить восстановление резервной копии новой БД в изолированной базе.
4. Развернуть конечный образ и подтвердить health, runtime revision, реальный
   вход администратора, контакты и контролируемую отправку через Telegram.

Rollback автоматически восстанавливает предыдущую версию приложения только
с последующей проверкой её health. База не восстанавливается автоматически:
это могло бы удалить новые записи. Резервная копия сохраняется для отдельного
решения о восстановлении. Политика хранения и независимая копия backups также
остаются эксплуатационной обязанностью.
