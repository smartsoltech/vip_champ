# Аудит VIP Champ и устранение замечаний

Дата: **20 октября 2026**, часовой пояс Asia/Seoul. Исходная проверенная ревизия:
`1f360a4`. Документ описывает исправления кода и подготовленную инфраструктуру;
**запуск реального бота ещё не выполнен**. По последнему уточнению пользователя
нужен новый запуск с пустой БД: старый бот не работает, исходных настроек и БД
для переноса нет. Миграция legacy-данных для этого развёртывания не требуется.

Проверены рабочие Python-модули, сценарии администрирования и импорта,
зависимости, Docker/Compose и отслеживаемые Git файлы. В исходном репозитории
было 346 tracked-файлов, включая 330 снимков `.history`. Аудит и тесты не доказывают
отсутствие любых возможных ошибок; ниже перечислены подтверждённые проблемы и
конкретные меры.

| Приоритет | Исходная проблема | Выполненные изменения |
|---|---|---|
| Высокий | В двух tracked-снимках `.history/.env*` обнаружены значения формата Telegram-токена; в одном — непустой пароль masteradmin. Проверка истории всех веток обнаружила 12 снимков с токенами. Их действительность не проверялась. | История очищена и отправлена в оба remote; свежие клоны прошли проверку. Добавлены ignore-правила и сканер секретов. Новый токен пользователь добавит отдельно; исторические значения не используются. |
| Высокий | `COPY . /app` включал историю, Git-метаданные и потенциальные локальные секреты/БД в образ. | Разрешающий список `.dockerignore`, отдельное копирование рабочих файлов, внешняя конфигурация с секретами. |
| Высокий | Недостаточная привязка административных действий к пользователю и сценарию; несогласованные проверки ролей. | Только личные чаты и числовой Telegram ID; проверка ролей и прав в обработчиках и транзакциях, ограничение попыток входа, TTL сессии, nonce меню с привязкой к сообщению и отправителю. |

| Средний | CSV-импорт и экспорт имели разные форматы, недостаточную валидацию и риск частичного импорта. | Единый обратимый формат, строгий UTF-8/структура/Telegram ID/размеры, защита от формул в таблицах, проверка всего файла до транзакции, учёт дубликатов и резервная копия перед изменениями. |

При повторном независимом ревью дополнительно устранены: сохранение сессии
после смены пароля/роли/привязки, возможность занять непривязанный legacy-аккаунт,
сохранение некорректного plaintext `password_hash` в quarantine, гонка отзыва
полномочий во время административной записи, конкурирующее восстановление
рассылок двумя процессами и пропуск освобождения ресурсов при ошибке удаления
heartbeat. Для legacy-администраторов теперь требуется явная привязка через
доверенный CLI; владелец данного развёртывания — Telegram ID `556399210`.
Один только ID не даёт доступа.

## Проверки и пределы подтверждения

- [Drone build 1](https://drone.smartsoltech.kr/trevor/vip_champ/1) подтвердил
  **96 тестов и 15 subtests**, включая PostgreSQL 16, семь сценариев
  deployment/rollback и 11 lifecycle-тестов. Проверки и сборка образа прошли.
  [GitHub Actions](https://github.com/smartsoltech/vip_champ/actions/runs/39399608849)
  также завершился успешно. Проверенная ревизия приложения — `d9725db`.
  Дополнительно пройдены ruff, разбор YAML, `bash -n` и `git diff --check`.
- Оба lock-файла прошли `pip-audit`: известных уязвимостей не обнаружено на
  момент проверки. Это проверка Python-зависимостей, а не всего Docker-образа.
- Свежие mirror-клоны обоих remote и локальный репозиторий проверены:
  **79 доступных blob-объектов, 0 находок** в каждом. Из всех веток удалены
  `.history`, `.cosine`, env-файлы, старые БД и CSV с клиентами.
  Выполнены локальная очистка reflog и `git gc --prune=now`.
  Это подтверждает очистку доступной истории, но не чужих клонов,
  резервных копий или недоступных внутренних кэшей хостингов.
  GitHub Dependabot после переиндексации показывает **0 открытых alerts**.
- Тесты deployment/rollback используют подставной Docker и не доказывают
  успешную доставку образа в рабочую среду. Отдельно выполнен реальный `pg_dump`
  с нового LXC: резервная копия инициализированной рабочей БД — 20 152 байта.
  Именно эта копия восстановлена штатным `pg_restore 16.15` в отдельную
  временную БД: количество строк и SHA-256 содержимого всех восьми таблиц
  совпали с production. Рабочая БД проверялась только через `READ ONLY`;
  временная БД удалена. Отдельно прошёл restore тестового набора с проверкой
  авторизации, последовательностей ID и очереди рассылки.
- Реальный первый deploy выявил недоступность вложенного backup-каталога
  для SSH-пользователя при корректных правах `0700` и владельце UID 10001.
  Проверка перенесена на доступный родительский каталог; резервное копирование
  выполняется под UID приложения. Закрытые права сохранены.
- `TELEGRAM_API_TOKEN` намеренно пуст по указанию пользователя. Проверка
  конфигурации предшествует backup и замене приложения. Живой polling,
  Telegram-авторизация и отправка сообщений пока не подтверждены.

## Что ещё требуется для завершения

1. В настройках Drone → Secrets заменить значение
   `vip_champ_telegram_api_token` на новый токен из BotFather. Начальное значение
   `CHANGE_ME_IN_DRONE_SETTINGS` — заглушка, блокирующая деплой.
   Пайплайн передаёт токен через SSH stdin и атомарно обновляет
   `/opt/vip_champ/shared/.env` на `192.168.50.250`, сохраняя права `0600`.
   В этом защищённом файле также находится начальный пароль администратора
   `owner`, привязанного к `556399210`.
2. Повторить последний pipeline в
   [Drone](https://drone.smartsoltech.kr/trevor/vip_champ).
   Деплой проверит конфигурацию, создаст backup, запустит контейнер и дождётся
   успешного Telegram polling и проверки БД перед обновлением `current`.
3. Проверить `/settings` от владельца и заполнить контакты/ссылки.
   После сохранения пароля владельцем удалить bootstrap credentials из
   конфигурации; запись администратора в БД сохраняется.

Основной remote — `backup` (`git.smartsoltech.kr`), GitHub — `origin`;
основная ветка — `master`. Старые клоны следует заменить свежими, чтобы
не вернуть очищенную историю. Сохранены только исходные SHA refs, без
отдельного архива удалённых секретов.

Rollback автоматически восстанавливает предыдущую версию приложения только
с последующей проверкой её health. База не восстанавливается автоматически:
это могло бы удалить новые записи. Резервная копия сохраняется для отдельного
решения о восстановлении. Политика хранения и независимая копия backups также
остаются эксплуатационной обязанностью.
